## What Phase 0.4 is

Phase 0.4 has one goal: make the CMS accessible to everyone.

The `cms create` scaffold command for developers. The browser-based installer for non-technical users. These two things together mean anyone — from a TypeScript developer to someone who has never opened a terminal — can get a running site.

Everything in this phase is about the first-run experience. Nothing in this phase is complex infrastructure — it’s polish, scaffolding, and the install path that determines whether people adopt the CMS or bounce.

**Done when:** A developer can scaffold a new site with `cms create` and be running in under two minutes. A non-technical user can paste one curl command, visit their domain, and complete a web installer to get a working site. The getting started doc reflects this correctly.

## Task 01 — `cms create` Command

**What it is:** The most important CLI command the CMS ships. Scaffolds a new site project that uses `@kritano/cms` as a versioned dependency. The user never clones the CMS repo. Updates are `bun update @kritano/cms` — no git conflicts, no merge headaches, no overwriting of user files.

**This is how every well-designed framework works:** `create-next-app`, `create-astro`, `laravel new`. The tool is separate from the project it creates.

-----

### How it works

```bash
# Install the CLI globally once
bun install -g @kritano/cms

# Create a new site
cms create my-site

# Or with options
cms create my-site --starter blog --no-git
```

**What `cms create my-site` does:**

1. Creates a `my-site/` directory
1. Copies the scaffold template (starter files — not the CMS internals)
1. Writes `package.json` with `@kritano/cms` as a dependency
1. Generates a `.env` with secure random secrets via `openssl rand`
1. Writes `.gitignore`
1. Runs `bun install` (installs `@kritano/cms` and its dependencies)
1. Runs `bun run migrate` (sets up the database schema)
1. Seeds sample content and admin user
1. Prints the success message with next steps

**Terminal output:**

```
  Creating Kritano CMS site in ./my-site

  ✓ Scaffold copied
  ✓ .env generated with secure secrets
  ✓ Dependencies installed
  ✓ Database migrated
  ✓ Sample content seeded

  Your site is ready.

  ┌─────────────────────────────────────────────┐
  │                                             │
  │   cd my-site                                │
  │   bun run dev                               │
  │                                             │
  │   Admin:    http://localhost:3006/admin     │
  │   Site:     http://localhost:3006           │
  │                                             │
  │   Email:    cms-admin@kritano.com                 │
  │   Password: admin                           │
  │                                             │
  └─────────────────────────────────────────────┘

  ⚠ Change your password after first login.
```

-----

### Scaffold template structure

The scaffold template lives at `packages/cli/templates/default/`. This is what gets copied to the user’s project — not the full monorepo.

```
packages/cli/templates/default/
├── cms.config.ts.template     ← starter schema (page + article + project)
├── package.json.template      ← @kritano/cms as dependency, scripts
├── .env.template              ← all required vars, secrets as {{SECRET_1}} placeholders
├── .gitignore
├── themes/
│   └── default/               ← copy of the default theme starter
│       ├── theme.config.ts
│       ├── layouts/
│       ├── templates/
│       ├── components/
│       ├── pages/
│       └── styles/
└── README.md                  ← minimal — points to full docs
```

`.template` files have `{{PLACEHOLDER}}` tokens replaced by the CLI during scaffolding:

- `{{SITE_NAME}}` — from the `--name` option or the directory name
- `{{JWT_SECRET}}` — generated via `crypto.randomBytes(32).toString('hex')`
- `{{REFRESH_SECRET}}` — same
- `{{VERSION}}` — current `@kritano/cms` version

-----

### CLI options

```bash
cms create <name>                   # Interactive mode — prompts for options
cms create <name> --starter blog    # Skip prompt, use blog starter
cms create <name> --no-git          # Skip git init
cms create <name> --no-install      # Skip bun install (just copy files)
cms create <name> --yes             # Accept all defaults, no prompts
```

**Interactive prompt (when no options given):**

```
? What would you like to call your site? › my-site
? Choose a starter template
  ❯ Default    — pages and articles, clean slate
    Blog       — blog-focused with tags, categories, featured posts
    Portfolio  — projects, case studies, about page
    Business   — pages, blog, team, services, contact form
? Initialise a git repository? › Yes
? Install dependencies now? › Yes
```

### The scaffold as a separate installable package

The `cms create` command is also available without installing the full CLI globally:

```bash
bunx @kritano/create-cms my-site
```

This follows the `create-*` convention (like `create-react-app`, `create-next-app`). The `@kritano/create-cms` package is a thin wrapper around the scaffold command. This means a user can run it without any prior global install — just `bunx` and go.

-----

### What the scaffolded project looks like

```
my-site/
├── cms.config.ts          ← your content schema — the main file you edit
├── themes/
│   └── default/           ← your theme — copy and customise freely
├── .env                   ← your environment config — never commit
├── .gitignore
├── package.json           ← @kritano/cms as a versioned dependency
├── bun.lock               ← commit this — it's your version pin
└── README.md
```

Nothing else. No `packages/`, no `server.ts`, no monorepo structure. The CMS internals live entirely inside `node_modules/@kritano/cms`. The user never sees them, never edits them, never conflicts with them.

**The user’s files are 100% theirs.** A CMS update (`bun update @kritano/cms`) touches only `node_modules` and `bun.lock`. Their theme, their schema, their content — untouched.

-----

### `package.json` of the scaffolded project

```json
{
  "name": "my-site",
  "private": true,
  "type": "module",
  "scripts": {
    "dev":      "cms dev",
    "build":    "cms build",
    "migrate":  "cms migrate",
    "generate": "cms generate"
  },
  "dependencies": {
    "@kritano/cms": "^0.4.0"
  }
}
```

The `cms` binary is provided by `@kritano/cms`. After `bun install` the user has access to all CLI commands.

-----

### Updating the CMS (scaffolded project)

```bash
bun update @kritano/cms   # update to latest compatible version
bun run migrate           # run any new migrations
bun run build             # rebuild frontend
```

No git pull. No merge conflicts. No risk of overwriting theme or schema files. The admin shows a notification when a new version is available — the user sees what changed and decides when to update.

**The one terminal command a non-technical user ever runs:**


This runs the server installation script (from the Deployment section). After it completes, the user visits their domain and sees the installer wizard instead of the admin. No more terminal required.

The installer shows when the CMS detects no admin user exists in the database. Once setup is complete and an admin account is created, the installer never shows again. Accessing `/install` after setup redirects to `/admin`.

### Installer implementation

```
packages/core/src/
└── installer/
    ├── index.ts          # Installer router — serves wizard if not configured
    ├── routes.ts         # GET /install, POST /install/step/:n
    ├── setup.ts          # Runs setup: creates admin, configures site, seeds content
    └── guard.ts          # Middleware — redirect /install to /admin if already configured
```

The installer is a set of Hono routes served at `/install`. The React admin SPA has an installer mode that renders the wizard steps when the `/install` routes are active.

**Setup process (on final step submission):**

1. Create admin user with provided credentials
1. Write site config (name, domain, language) to database
1. Apply the selected starter’s schema to `cms.config.ts` on the server
1. Run migrations for the selected starter
1. Seed starter content
1. Mark installation complete (set `cms_configured: true` in site settings)
1. Return session token — user is logged in immediately

**Security:**

- Installer routes are only accessible if `cms_configured` is false in the database
- Once configured, all `/install` routes return 302 to `/admin`
- Rate limited — max 10 requests per IP per hour to prevent brute force

## Phase 0.4.2 — Plugin Registry & One-Click Install

**What it is:** A plugin discovery and installation system built into the admin UI. Users browse available plugins and install them with one click — like WordPress’s "Add New" plugin page. All plugins are GitHub repos under the Kritano org. Local plugin development via the `plugins/` directory continues to work unchanged.

-----

### How it works

1. A `plugins.json` registry file lives in the CMS repo root (`https://raw.githubusercontent.com/Kritano/Kritano-cms/main/plugins.json`)
2. The admin Plugins page has an "Available" tab that fetches this registry
3. Users click "Install" on any plugin → the API runs `bun add github:Kritano/<plugin-repo>` and adds it to `cms.config.ts`
4. Local plugins in `plugins/` directory are auto-discovered as before — no install needed

-----

### Registry format

```
plugins.json (in CMS repo root)
```

```json
{

    {
      "name": "@kritano/cms-plugin-newsletter",
      "repo": "Kritano/cms-plugin-newsletter",
      "description": "Newsletter and subscriber management",

      "author": "Kritano",
      "trust": "trusted",
      "tags": ["email", "subscribers", "marketing"],
      "icon": "mail"
    },
    {
      "name": "@kritano/cms-plugin-analytics",
      "repo": "Kritano/cms-plugin-analytics",
      "description": "Simple analytics dashboard — page views, referrers, top content",
      "version": "0.1.0",
      "author": "Kritano",
      "trust": "trusted",
      "tags": ["analytics", "tracking"],
      "icon": "bar-chart"
    },
    {
      "name": "@kritano/cms-plugin-seo",
      "repo": "Kritano/cms-plugin-seo",
      "description": "Advanced SEO tools — sitemap customisation, structured data, meta previews",

```

The registry is a static JSON file — no server, no database, no authentication. Adding a new plugin means adding an entry to this file and pushing to `main`. The admin fetches it via the GitHub raw URL.

-----

### New API routes

```
GET   /api/admin/plugins/available        Fetch registry, merge with installed status
POST  /api/admin/plugins/install          Install a plugin from GitHub
```

**`GET /api/admin/plugins/available`:**

Fetches `plugins.json` from GitHub (cached for 1 hour), cross-references with installed plugins, returns the merged list.

```typescript
{
  plugins: [
    {
      name: ‘@kritano/cms-plugin-newsletter’,
      repo: ‘Kritano/cms-plugin-newsletter’,
```

# Block Viewer — Build Task Document
**Two-level visual block discovery system**
**For use with Kritano Team Skill / Claude Code Manager**
**Phase:** 0.1 (Level 1 — visual block picker in editor) / 0.2 (Level 2 — block library page)

---

## Overview

The block viewer solves a real editorial problem: content editors have no way to see what block types exist, what they look like, or what fields they contain without trial and error. This is one of the worst parts of every CMS with flexible content — editors discover blocks by clicking through them blind.

The block viewer makes this completely unnecessary. It exists at two levels:

**Level 1 — Visual block picker** (in the document editor)
When an editor adds a block to a page, instead of seeing a plain text list of block names, they see a visual card picker with thumbnail previews, descriptions, and field summaries. Embedded directly into the editor workflow.

**Level 2 — Block library page** (standalone admin page)
A dedicated admin page showing every block type defined across all collections — full-size previews, complete field documentation, usage information. A reference that's always in sync with the actual schema because it's generated from it.

---

## Level 1 — Visual Block Picker

### Where it appears

When an editor is building a page with a `blocks()` field, they add new blocks via:

1. The `/` slash command in the editor
2. The **Add block** button at the bottom of the block list
3. The `+` button that appears between existing blocks on hover

All three currently show a plain list of block type names. All three are replaced with the visual picker.

### Block thumbnails

Each block type needs a visual thumbnail. Two approaches, both supported:

**Approach A — Static preview images (default)**

The theme developer creates a thumbnail image for each block and places it in the theme:

```
themes/my-theme/
└── block-previews/
    ├── hero.png
    ├── text.png
    ├── image-text.png
    ├── cta.png
    ├── gallery.png
    └── testimonial.png
```

Images should be:
- 16:9 aspect ratio
- 640×360px minimum
- PNG or WebP
- Show a representative example of the block rendered with real-looking content — not wireframes, not placeholder boxes

The CMS serves these from the theme directory. If a preview image is missing for a block, a fallback is shown (see below).

**Approach B — Auto-generated placeholder (fallback)**

If no preview image exists for a block, the picker generates a placeholder that communicates the block's structure visually. This is generated at runtime from the block's field definitions:

```
┌──────────────────────────────┐
│  ████████████████████        │  ← represents a heading field
│  ████████████                │  ← represents a subheading
│                              │
│  ┌──────────────────────┐    │
│  │                      │    │  ← represents a media field
│  │    [image]           │    │
│  │                      │    │
│  └──────────────────────┘    │
│                              │
│  [Button text]               │  ← represents a CTA field
└──────────────────────────────┘
```

The placeholder uses the field types to determine what to draw:
- `text()` / `textarea()` → horizontal grey bars
- `richText()` → multiple short grey bars (paragraph simulation)
- `media()` → grey rectangle with image icon
- `boolean()` → toggle illustration
- `select()` → dropdown illustration
- `url()` / `text()` marked as CTA → button shape

This means every block has a meaningful visual representation even before the theme developer creates custom screenshots.

## Preview image generation — technical detail

### Static images served from theme

The API serves static preview images from the theme directory:

```typescript
// GET /api/admin/blocks/preview/:type
app.get('/blocks/preview/:type', requireAuth, async (c) => {
  const blockType = c.req.param('type')
  const theme = await getActiveTheme()

  const previewPath = theme.blockPreviews?.[blockType]

  if (previewPath) {
    // Serve the static image from the theme directory
    const file = await readThemeFile(previewPath)
    return new Response(file, {
      headers: {
        'Content-Type': getImageMimeType(previewPath),
        'Cache-Control': 'public, max-age=3600',
      }
    })
  }

  // No custom image — generate fallback
  return generateFallbackPreview(blockType, c)
})
```

### Auto-generated fallback

The fallback uses `@resvg/resvg-js` (an SVG renderer) to generate a PNG preview from an SVG template built from the block's field definitions:

```typescript
async function generateFallbackPreview(
  blockType: string,
  c: HonoContext
): Promise<Response> {

  const blockDef = cms.schema.getBlock(blockType)
  const svg = renderBlockPreviewSvg(blockDef)

  const resvg = new Resvg(svg, { fitTo: { mode: 'width', value: 640 } })
  const png = resvg.render().asPng()

  return new Response(png, {
    headers: {
      'Content-Type': 'image/png',
      'Cache-Control': 'public, max-age=300',
      'X-Preview-Type': 'auto-generated',
    }
  })
}

function renderBlockPreviewSvg(blockDef: BlockDefinition): string {
  // Build SVG that visually represents the block structure
  // based on its field types
  const elements: string[] = []
  let y = 20

  for (const [fieldName, fieldDef] of Object.entries(blockDef.fields)) {
    switch (fieldDef.type) {
      case 'text':
        // Draw a text line — width varies by assumed content length
        elements.push(`<rect x="20" y="${y}" width="${fieldName === 'heading' ? 400 : 280}" height="20" rx="4" fill="#e2e8f0"/>`)
        y += 36
        break
      case 'textarea':
      case 'richText':
        // Draw multiple lines to represent a text block
        for (let i = 0; i < 3; i++) {
          elements.push(`<rect x="20" y="${y + i * 24}" width="${560 - i * 80}" height="14" rx="3" fill="#e2e8f0"/>`)
        }
        y += 90
        break
      case 'media':
        // Draw an image placeholder rectangle
        elements.push(`<rect x="20" y="${y}" width="560" height="200" rx="8" fill="#f1f5f9"/>`)
        elements.push(`<text x="300" y="${y + 105}" text-anchor="middle" fill="#94a3b8" font-size="14">image</text>`)
        y += 220
        break
      case 'url':
        // Draw a button shape if this looks like a CTA
        if (fieldName.toLowerCase().includes('cta') || fieldName.toLowerCase().includes('button')) {
          elements.push(`<rect x="20" y="${y}" width="160" height="44" rx="6" fill="#334155"/>`)
          elements.push(`<text x="100" y="${y + 27}" text-anchor="middle" fill="white" font-size="13">Button</text>`)
        } else {
          elements.push(`<rect x="20" y="${y}" width="300" height="20" rx="4" fill="#e2e8f0"/>`)
        }
        y += 60
        break
      case 'select':
        // Draw a dropdown shape
        elements.push(`<rect x="20" y="${y}" width="200" height="36" rx="6" fill="white" stroke="#e2e8f0" stroke-width="2"/>`)
        elements.push(`<text x="100" y="${y + 23}" text-anchor="middle" fill="#94a3b8" font-size="12">Select...</text>`)
        y += 52
        break
    }
  }

  return `
    <svg width="600" height="${y + 40}" viewBox="0 0 600 ${y + 40}" xmlns="http://www.w3.org/2000/svg">
      <rect width="600" height="${y + 40}" fill="#f8fafc"/>
      ${elements.join('\n')}
    </svg>
  `
}
```

## Live preview route

The live preview renders the actual Astro block component server-side with provided field values:

```typescript
// GET /api/admin/blocks/live-preview/:type?heading=Hello&image=media-id
app.get('/blocks/live-preview/:type', requireAuth, async (c) => {
  const blockType = c.req.param('type')
  const fieldValues = c.req.query()  // field values from query params

  // Find the theme component for this block type
  const theme = await getActiveTheme()
  const componentPath = theme.blockComponents?.[blockType]

  if (!componentPath) {
    return c.json({ error: 'No component registered for this block type' }, 404)
  }

  // Render the Astro component with the provided field values
  // This calls Astro's server-side render API
  const html = await renderAstroComponent(componentPath, {
    fields: fieldValues,
    isPreview: true,
  })

  // Wrap in a minimal HTML document
  return c.html(`
    <!DOCTYPE html>
    <html>
    <head>
      <meta charset="utf-8">
      <meta name="viewport" content="width=device-width, initial-scale=1">
      <link rel="stylesheet" href="${getThemeStylesheetUrl()}">
      <style>body { margin: 0; padding: 0; }</style>
    </head>
    <body>
      ${html}
    </body>
    </html>
  `)
})
```

The `isPreview: true` prop is passed to the component so it can use placeholder images instead of trying to load real media by ID.
