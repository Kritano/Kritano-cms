## What Phase 0.4 is

Phase 0.4 has one goal: make the CMS accessible to everyone.

The `cms create` scaffold command for developers. The browser-based installer for non-technical users. These two things together mean anyone — from a TypeScript developer to someone who has never opened a terminal — can get a running site.

Everything in this phase is about the first-run experience. Nothing in this phase is complex infrastructure — it’s polish, scaffolding, and the install path that determines whether people adopt the CMS or bounce.

**Done when:** A developer can scaffold a new site with `cms create` and be running in under two minutes. A non-technical user can paste one curl command, visit their domain, and complete a web installer to get a working site. The getting started doc reflects this correctly.

## Task 01 — `cms create` Command

**What it is:** The most important CLI command the CMS ships. Scaffolds a new site project that uses `@kritano/cms` as a versioned dependency. The user never clones the CMS repo. Updates are `bun update @kritano/cms` — no git conflicts, no merge headaches, no overwriting of user files.

**This is how every well-designed framework works:** `create-next-app`, `create-astro`, `laravel new`. The tool is separate from the project it creates.

-----

### How it works

```bash
# Install the CLI globally once
bun install -g @kritano/cms

# Create a new site
cms create my-site

# Or with options
cms create my-site --starter blog --no-git
```

**What `cms create my-site` does:**

1. Creates a `my-site/` directory
1. Copies the scaffold template (starter files — not the CMS internals)
1. Writes `package.json` with `@kritano/cms` as a dependency
1. Generates a `.env` with secure random secrets via `openssl rand`
1. Writes `.gitignore`
1. Runs `bun install` (installs `@kritano/cms` and its dependencies)
1. Runs `bun run migrate` (sets up the database schema)
1. Seeds sample content and admin user
1. Prints the success message with next steps

**Terminal output:**

```
  Creating Kritano CMS site in ./my-site

  ✓ Scaffold copied
  ✓ .env generated with secure secrets
  ✓ Dependencies installed
  ✓ Database migrated
  ✓ Sample content seeded

  Your site is ready.

  ┌─────────────────────────────────────────────┐
  │                                             │
  │   cd my-site                                │
  │   bun run dev                               │
  │                                             │
  │   Admin:    http://localhost:3006/admin     │
  │   Site:     http://localhost:3006           │
  │                                             │
  │   Email:    cms-admin@kritano.com                 │
  │   Password: admin                           │
  │                                             │
  └─────────────────────────────────────────────┘

  ⚠ Change your password after first login.
```

-----

### Scaffold template structure

The scaffold template lives at `packages/cli/templates/default/`. This is what gets copied to the user’s project — not the full monorepo.

```
packages/cli/templates/default/
├── cms.config.ts.template     ← starter schema (page + article + project)
├── package.json.template      ← @kritano/cms as dependency, scripts
├── .env.template              ← all required vars, secrets as {{SECRET_1}} placeholders
├── .gitignore
├── themes/
│   └── default/               ← copy of the default theme starter
│       ├── theme.config.ts
│       ├── layouts/
│       ├── templates/
│       ├── components/
│       ├── pages/
│       └── styles/
└── README.md                  ← minimal — points to full docs
```

`.template` files have `{{PLACEHOLDER}}` tokens replaced by the CLI during scaffolding:

- `{{SITE_NAME}}` — from the `--name` option or the directory name
- `{{JWT_SECRET}}` — generated via `crypto.randomBytes(32).toString('hex')`
- `{{REFRESH_SECRET}}` — same
- `{{VERSION}}` — current `@kritano/cms` version

-----

### CLI options

```bash
cms create <name>                   # Interactive mode — prompts for options
cms create <name> --starter blog    # Skip prompt, use blog starter
cms create <name> --no-git          # Skip git init
cms create <name> --no-install      # Skip bun install (just copy files)
cms create <name> --yes             # Accept all defaults, no prompts
```

**Interactive prompt (when no options given):**

```
? What would you like to call your site? › my-site
? Choose a starter template
  ❯ Default    — pages and articles, clean slate
    Blog       — blog-focused with tags, categories, featured posts
    Portfolio  — projects, case studies, about page
    Business   — pages, blog, team, services, contact form
? Initialise a git repository? › Yes
? Install dependencies now? › Yes
```

-----

### The scaffold as a separate installable package

The `cms create` command is also available without installing the full CLI globally:

```bash
bunx @kritano/create-cms my-site
```

This follows the `create-*` convention (like `create-react-app`, `create-next-app`). The `@kritano/create-cms` package is a thin wrapper around the scaffold command. This means a user can run it without any prior global install — just `bunx` and go.

-----

### What the scaffolded project looks like

```
my-site/
├── cms.config.ts          ← your content schema — the main file you edit
├── themes/
│   └── default/           ← your theme — copy and customise freely
├── .env                   ← your environment config — never commit
├── .gitignore
├── package.json           ← @kritano/cms as a versioned dependency
├── bun.lock               ← commit this — it's your version pin
└── README.md
```

Nothing else. No `packages/`, no `server.ts`, no monorepo structure. The CMS internals live entirely inside `node_modules/@kritano/cms`. The user never sees them, never edits them, never conflicts with them.

**The user’s files are 100% theirs.** A CMS update (`bun update @kritano/cms`) touches only `node_modules` and `bun.lock`. Their theme, their schema, their content — untouched.

-----

### `package.json` of the scaffolded project

```json
{
  "name": "my-site",
  "private": true,
  "type": "module",
  "scripts": {
    "dev":      "cms dev",
    "build":    "cms build",
    "migrate":  "cms migrate",
    "generate": "cms generate"
  },
  "dependencies": {
    "@kritano/cms": "^0.4.0"
  }
}
```

The `cms` binary is provided by `@kritano/cms`. After `bun install` the user has access to all CLI commands.

-----

### Updating the CMS (scaffolded project)

```bash
bun update @kritano/cms   # update to latest compatible version
bun run migrate           # run any new migrations
bun run build             # rebuild frontend
```

No git pull. No merge conflicts. No risk of overwriting theme or schema files. The admin shows a notification when a new version is available — the user sees what changed and decides when to update.

## Task 02 — Browser-Based Installer

**What it is:** A web wizard that runs when the CMS is installed on a server but not yet configured. Targeted at users who can follow a basic guide but don’t want to work in a terminal beyond running one installation script.

**The one terminal command a non-technical user ever runs:**

```bash
curl -fsSL https://get.kritano.com | bash
```

This runs the server installation script (from the Deployment section). After it completes, the user visits their domain and sees the installer wizard instead of the admin. No more terminal required.

-----

### Installer trigger

The installer shows when the CMS detects no admin user exists in the database. Once setup is complete and an admin account is created, the installer never shows again. Accessing `/install` after setup redirects to `/admin`.

-----

### Installer implementation

```
packages/core/src/
└── installer/
    ├── index.ts          # Installer router — serves wizard if not configured
    ├── routes.ts         # GET /install, POST /install/step/:n
    ├── setup.ts          # Runs setup: creates admin, configures site, seeds content
    └── guard.ts          # Middleware — redirect /install to /admin if already configured
```

The installer is a set of Hono routes served at `/install`. The React admin SPA has an installer mode that renders the wizard steps when the `/install` routes are active.

**Setup process (on final step submission):**

1. Create admin user with provided credentials
1. Write site config (name, domain, language) to database
1. Apply the selected starter’s schema to `cms.config.ts` on the server
1. Run migrations for the selected starter
1. Seed starter content
1. Mark installation complete (set `cms_configured: true` in site settings)
1. Return session token — user is logged in immediately

**Security:**

- Installer routes are only accessible if `cms_configured` is false in the database
- Once configured, all `/install` routes return 302 to `/admin`
- Rate limited — max 10 requests per IP per hour to prevent brute force

# Updating Kritano CMS

## If you used cms create (recommended)

Your site uses @kritano/cms as a versioned dependency. Updates are clean —
