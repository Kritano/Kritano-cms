## What Phase 0.3 is

Phase 0.3 turns the CMS into an extensible platform. The community can now build and publish plugins. Search works out of the box. OAuth reduces signup friction. Live preview works with any frontend framework.

The plugin system is the most important piece in this phase — it must come first because everything else in 0.3 could theoretically be built as a plugin. Getting the plugin API right before anything else is essential.

**Done when:** A developer can install a community plugin via the CLI or admin UI and it works. Full-text search returns results across all collections. Users can log in with Google or GitHub. A developer can connect any frontend framework to live preview mode.

### Plugin definition

```typescript
import { definePlugin } from '@cms/core'

export default definePlugin({
  name: '@cms-plugin/newsletter',
  version: '1.2.0',

  author: 'Kritano',

  // Trust tier — see Trust Model below
  // 'trusted' = in-process, full API access
  // 'sandboxed' = isolated-vm, restricted API surface

  // Minimum and maximum CMS version this plugin supports

    minVersion: '0.3.0',
    maxVersion: '1.x',
  },

  // Other plugins this plugin requires to be installed and enabled
  requires: [],

  setup(context) {
    // context is PluginContext — all extension points live here
  }
})
```

### Trust model

Plugins run in one of two modes. The trust tier is declared in the plugin manifest and enforced by the loader.

**Trusted — in-process**

Runs in the same V8 isolate as the CMS. Full `PluginContext` API available. No overhead. Used for:

- All official `@cms-plugin/*` packages
- Local plugins in the `plugins/` directory
- Community plugins the user explicitly marks as trusted in `cms.config.ts`

**Sandboxed — isolated-vm**

Runs in a separate V8 isolate via `isolated-vm`. Separate heap, separate garbage collector. A crash or infinite loop inside the isolate cannot bring down the CMS. A restricted `PluginContext` is exposed — only safe, serialisable operations. Used for:

- Community plugins from the registry not yet verified
- Any plugin with `trust: 'sandboxed'` in its manifest

**Verified — trusted after review**

Community plugins that have been reviewed by the Kritano team. Listed on the registry with a verified badge. Users can install them as trusted. Promotion from sandboxed to verified happens via a manual audit process documented on the registry site.

**Trust override in `cms.config.ts`:**

```typescript
export default defineConfig({
  plugins: [
    '@cms-plugin/newsletter',                          // trusted (official)
    ['community-plugin-x', { trust: 'trusted' }],     // user override — at own risk
    ['community-plugin-y', { trust: 'sandboxed' }],   // explicit sandboxed (default for community)
  ],
})
```

### Sandboxing — isolated-vm implementation

```typescript
// packages/core/src/plugins/sandbox.ts
import ivm from 'isolated-vm'

const MEMORY_LIMIT_MB = 128

export async function createSandboxedContext(pluginCode: string): Promise<SandboxedPlugin> {
  const isolate = new ivm.Isolate({ memoryLimit: MEMORY_LIMIT_MB })
  const context = await isolate.createContext()

  // Inject ONLY the restricted API surface
  // Sandboxed plugins cannot: access fs, make arbitrary network requests,
  // require modules, access env vars, or touch CMS internals directly
  await context.global.set('cms', new ivm.Reference({
    hooks: {
      on: ivm.Reference.create(sandboxedHookRegistration),
    },
    collections: {
      findMany: ivm.Reference.create(sandboxedCollectionQuery),
      findOne:  ivm.Reference.create(sandboxedCollectionFindOne),
      create:   ivm.Reference.create(sandboxedCollectionCreate),
      update:   ivm.Reference.create(sandboxedCollectionUpdate),
    },
    storage: {
      get: ivm.Reference.create(sandboxedStorageGet),
      set: ivm.Reference.create(sandboxedStorageSet),
    },
    config: {
      get: ivm.Reference.create(sandboxedConfigGet),
    },
    // Sandboxed plugins explicitly CANNOT access:
    // api (register routes), admin (register UI), fields (register field types),
    // collections.register(), schema.extend(), jobs.register()
    // These require trusted status
  }))

  const script = await isolate.compileScript(pluginCode)
  await script.run(context)

  return { isolate, context }
}
```

**What sandboxed plugins can do:**

- Subscribe to content hooks
- Query and write to collections via the safe wrapper
- Read and write to their own plugin storage
- Read their own config

**What sandboxed plugins cannot do:**

- Register API routes
- Register admin UI sections or editor tabs
- Register custom field types
- Register new collections
- Extend the GraphQL schema
- Register background job handlers
- Access the filesystem
- Make arbitrary network requests
- Access environment variables
- Import npm modules not pre-approved

**Communication overhead:**

All data crossing the isolate boundary is serialised (copied, not referenced). This adds microseconds per call — negligible next to database round trips. A plugin doing `cms.collections.findMany()` will not notice the overhead. A plugin doing 10,000 tiny synchronous calls in a tight loop would — but that is not a typical CMS plugin pattern.

**Graceful fallback:**

`isolated-vm` requires native compilation via `node-gyp`. If compilation fails on the user’s server, the sandbox system falls back to warning-only mode:

```
[CMS] Warning: isolated-vm native addon failed to compile.
      Community plugins will run without sandboxing.
      Only install plugins you trust.
      See: docs.[name].kritano.com/plugins/sandboxing
```

The CMS still starts. Community plugins run in-process with a warning. This is documented clearly — sandboxing is a hardening layer, not a hard requirement for the CMS to function. The fallback is safe enough for plugins from the curated registry; it is not safe for unknown plugins.

### PluginContext — full API surface (trusted plugins)

```typescript
interface PluginContext {

  // --- Hooks ---
  hooks: {
    on(
      event: PluginHookEvent,
      handler: PluginHookHandler,
      options?: { order?: number }    // execution order — lower runs first, default 100
    ): void
  }

  // --- API ---
  // Register additional Hono routes — namespaced under /api/plugins/:pluginName/
  api: {
    get(path: string, handler: HonoHandler): void
    post(path: string, handler: HonoHandler): void
    put(path: string, handler: HonoHandler): void
    patch(path: string, handler: HonoHandler): void
    delete(path: string, handler: HonoHandler): void
  }

  // --- Admin UI ---
  admin: {
    registerSection(config: AdminSection): void
    registerEditorTab(config: EditorTab): void
    registerDashboardWidget(config: DashboardWidget): void
    registerSettingsPage(config: SettingsPage): void
  }

  // --- Fields ---
  // Field type names must be namespaced: 'plugin-name/field-type'
  fields: {
    register(type: string, component: React.ComponentType): void
  }

  // --- Collections ---
  collections: {
    register(collection: CollectionDefinition): void
  }

  // --- Schema ---
  schema: {
    extend(typeDefs: string): void
    addResolver(typeName: string, fieldName: string, resolver: GraphQLResolver): void
  }

  // --- Jobs ---
  jobs: {
    register(queueName: string, handler: JobHandler): void
    enqueue(queueName: string, data: unknown, options?: JobOptions): Promise<void>
  }

  // --- Config ---
  config: {
    get<T>(key: string): T | undefined
    getAll(): Record<string, unknown>
  }

  // --- Storage ---
  storage: {
    get(key: string): Promise<unknown>
    set(key: string, value: unknown): Promise<void>
    delete(key: string): Promise<void>
  }

  // --- CMS services ---
  cms: {
    collections: CollectionService
    media: MediaService
    users: UserService
  }
}
```

Hook handlers receive a context object with the relevant data. `before` hooks also receive a `cancel(reason: string)` function to abort the operation. Multiple plugins can subscribe to the same event — they fire in `order` sequence.

### Conflict detection

The loader runs conflict checks before initialising any plugin. A conflict is a hard startup error with a clear message — not a warning, not a silent override.

**Conflicts that are hard errors:**

```typescript
// Route conflict
// Two plugins register the same HTTP method + path
// Error: Plugin conflict: @cms-plugin/a and @cms-plugin/b both register GET /api/plugins/my-route

// Field type conflict
// Two plugins register the same field type name
// Error: Plugin conflict: plugin-a and plugin-b both register field type 'newsletter/picker'
// Prevention: field types MUST be namespaced as 'plugin-name/type-name'

// Collection name conflict
// Two plugins register a collection with the same name, or a plugin uses a name
// already defined in cms.config.ts
// Error: Plugin conflict: @cms-plugin/x tries to register collection 'subscriber'
//        which already exists

// Admin section path conflict
// Two plugins register the same admin section path
// Error: Plugin conflict: plugin-a and plugin-b both register admin section at /admin/plugins/my-section
```

**Conflict check implementation:**

```typescript

  const adminSections = new Map<string, string>()   // '/admin/path' → pluginName
  const errors: string[] = []

  for (const plugin of plugins) {
    // Check each registration against existing registrations
    // Populate errors array for any conflict found
  }

  return { errors, hasConflicts: errors.length > 0 }
}
```

On startup, if `hasConflicts` is true, log all errors and exit with a non-zero code. Do not partially start — a partially started CMS with some plugins loaded and others not is harder to debug than a clean failure.

**Hook order — not a conflict, but documented:**

Multiple plugins subscribing to the same hook is expected and fine. They fire in `order` sequence. Plugins with the same order value fire in installation order. Document this clearly for plugin authors.

### Dependency resolution

```typescript
export default definePlugin({
  name: '@cms-plugin/commerce-stripe',
  requires: ['@cms-plugin/commerce'],  // must be installed and enabled
  // ...
})
```

**Dependency check on startup:**

For each plugin with `requires` declarations:

1. Check each required plugin is installed
1. Check each required plugin is enabled
1. If any requirement is missing: skip the dependent plugin with a clear error log

```
[CMS] Plugin @cms-plugin/commerce-stripe requires @cms-plugin/commerce
      which is not installed. Skipping @cms-plugin/commerce-stripe.
      Run: cms plugin:install @cms-plugin/commerce
```

**Dependency check on install (CLI):**

`cms plugin:install @cms-plugin/commerce-stripe` checks the plugin’s `requires` field and prompts:

```
@cms-plugin/commerce-stripe requires @cms-plugin/commerce.
Install @cms-plugin/commerce as well? [Y/n]
```

If yes, installs both in the correct order.

**Plugin `package.json` required fields:**

```json

  "name": "@cms-plugin/newsletter",

  "type": "module",
  "main": "./dist/index.js",
  "exports": {
    ".": "./dist/index.js"
```

**Version check on install:**

```typescript
// cms plugin:install @cms-plugin/newsletter
const cmsVersion = getCmsVersion()
const pluginMeta = readPluginPackageJson('@cms-plugin/newsletter')

if (!semver.satisfies(cmsVersion, `>=${pluginMeta.cms.minVersion}`)) {
  console.warn(`
    Warning: @cms-plugin/newsletter requires CMS >= ${pluginMeta.cms.minVersion}

  `)

```

**Version check on startup:**

For every installed plugin, check version compatibility. Incompatible plugins log a warning but do not prevent startup — the CMS starts, the plugin loads, but the admin shows a warning badge on the plugin.

```

      You are running CMS 1.0.0. The plugin may behave unexpectedly.
```

### Package naming conventions

```
Official Kritano plugins:   @cms-plugin/newsletter
Community plugins:          cms-plugin-my-thing     (no scope)
Community verified:         @cms-verified/my-thing  (once registry is established)
Local dev plugins:          no npm name required
```

Using `@cms-plugin/` scope for official plugins prevents community squatting on the primary namespace. Community plugins use an unscoped `cms-plugin-` prefix convention. This is documented clearly in `docs/plugins/building-plugins.md`.

### Plugin loader — updated sequence

```
1.  Discover all plugins (npm declared in cms.config.ts + local plugins/ directory)
2.  Read each plugin's package.json — validate cms.minVersion / maxVersion
3.  Log version warnings for out-of-range plugins (do not skip, just warn)
4.  Resolve dependency graph — determine load order based on requires declarations
5.  Check for missing dependencies — skip dependent plugins with clear error log
6.  Run conflict detection across all plugins to be loaded
7.  If any conflicts found — log all conflict errors and exit (hard fail)
8.  For each plugin in dependency order:
    a. If trusted: initialise in-process with full PluginContext
    b. If sandboxed: attempt isolated-vm initialisation with restricted context
       - If isolated-vm unavailable: log fallback warning, initialise in-process
    c. If plugin throws during setup: log error, skip plugin, continue with others
9.  Fire cms.ready hook
10. CMS begins serving requests
11. Log summary: "X plugins loaded, Y warnings, Z skipped"
```

**Plugin injection points in the admin:**

The admin UI needs to support dynamic injection of plugin-registered components. This requires a plugin UI registry that the React app reads on load.

The API serves registered plugin UI metadata at:

```
GET /api/admin/plugins/registry
```

Response:

```typescript
{
  sections: [
    {
      pluginName: 'my-plugin',
      label: 'My Plugin',
      icon: 'puzzle',
      path: '/admin/plugins/my-plugin/section',
```

Plugin admin components are served as pre-bundled ESM modules by the API. The admin SPA loads them dynamically using `React.lazy()` and a dynamic `import()`. This keeps the core admin bundle size constant regardless of how many plugins are installed.

## Task 04 — Typesense — Setup & Sync

**What it is:** Typesense integration — collection schema sync, document indexing on publish, and index management.

**What Typesense is:** A self-hosted, typo-tolerant full-text search engine. Fast, simple to operate, and requires no external cloud dependency. Runs as a separate process on the same server.

**New package additions:**

```
packages/core/src/
├── search/
│   ├── client.ts         # Typesense client wrapper
│   ├── schema-sync.ts    # CMS schema → Typesense collection schema
│   ├── indexer.ts        # Document indexing and removal
│   └── queries.ts        # Search query builder
```

**Typesense client config (from environment):**

```
TYPESENSE_HOST=localhost
TYPESENSE_PORT=8108
TYPESENSE_PROTOCOL=http
TYPESENSE_API_KEY=your-typesense-api-key
```

If these env vars are not set, search is gracefully disabled — no errors thrown, search endpoints return an empty result with a `search_unavailable: true` flag.

**CMS schema → Typesense schema:**

On CMS startup (and on `cms generate`), sync each collection’s schema to a Typesense collection:

```typescript
// CMS field type → Typesense field type mapping
const fieldTypeMap = {
  text:        { type: 'string' },
  textarea:    { type: 'string' },
  richText:    { type: 'string' },          // extract plain text from TipTap JSON
  slug:        { type: 'string' },
  url:         { type: 'string' },
  number:      { type: 'float' },
  boolean:     { type: 'bool' },
  datetime:    { type: 'int64' },           // Unix timestamp
  select:      { type: 'string', facet: true },
  multiSelect: { type: 'string[]', facet: true },
  // media, relation, seoBlock, blocks — not directly indexed
}
```

Every Typesense collection automatically includes:

- `id` — string (document UUID)
- `collection` — string (collection name, for cross-collection search)
- `status` — string (facet field)
- `publishedAt` — int64 (Unix timestamp, for sorting)
- `title` — string (always present, primary search field)

**Document indexing:**

Hook into the `content.afterPublish` and `content.afterUpdate` hooks to index documents:

```typescript
hooks.on('content.afterPublish', async ({ document, collection }) => {
  await indexer.upsert(collection, document)
})

hooks.on('content.afterUnpublish', async ({ document, collection }) => {
  await indexer.delete(collection, document.id)
})

hooks.on('content.afterDelete', async ({ document, collection }) => {
  await indexer.delete(collection, document.id)
})
```

Only published documents are indexed. Drafts are never in the search index.

**Plain text extraction from richText:**

TipTap JSON needs to be converted to plain text for indexing:

```typescript
function extractText(tiptapJson: TipTapContent): string {
  // Recursively extract text nodes from TipTap JSON
  // Ignore marks, keep all text content
  // Join with spaces
}
```

**Index management commands:**

```bash
cms search:sync        # Full re-index of all published documents across all collections
cms search:clear       # Clear all search indexes (useful during development)
```

**Done when:** On CMS startup, Typesense collections are created/updated to match the CMS schema. Publishing a document adds it to the index. Unpublishing removes it. `cms search:sync` re-indexes all published content. If Typesense is unavailable, CMS starts normally with search gracefully disabled.

## Task 08 — Live Preview Protocol

**What it is:** A standardised preview handshake between the CMS and any frontend framework. Editors can see draft content rendered in real-time before publishing.

**How live preview works:**

1. Editor opens a document in the admin
1. Clicks “Preview” — a preview window opens showing the live site
1. The preview URL contains a signed preview token: `https://mysite.com/my-page?cms_preview=<token>`
1. The frontend checks for the `cms_preview` param, validates the token, fetches draft content from the API using the token
1. Content updates in the editor are pushed to the preview window in real-time via the preview token

**Preview token:**

```typescript
interface PreviewToken {
  documentId: string
  collection: string
  exp: number              // expiry timestamp — tokens valid for 2 hours
}
// Signed with the CMS JWT secret — not forgeable
```

**New API routes:**

```
POST  /api/preview/token              Generate a preview token for a document
GET   /api/preview/validate           Validate a preview token (used by frontends)
GET   /api/:collection/:id/preview    Get draft content using preview token
```

**`POST /api/preview/token`:**

Auth required (admin only). Request body: `{ documentId, collection }`. Returns a signed preview token valid for 2 hours.

**`GET /api/:collection/:id/preview`:**

Public endpoint but requires valid `cms_preview` query param. Returns the draft document if the token is valid. This is the only public endpoint that returns draft content.

**Admin UI — preview button:**

Add a “Preview” button to the editor toolbar (next to Publish). Clicking:

1. POSTs to `/api/preview/token` to get a token
1. Constructs the preview URL: `{siteUrl}/{collection}/{slug}?cms_preview={token}`
1. Opens the URL in a new tab

For themes that support live refresh, also opens a preview panel inside the admin (iframe, 50/50 split with the editor). The preview panel refreshes after each autosave.

**`@cms/astro` — preview mode integration:**

The Astro integration handles preview automatically when the `cms_preview` param is present:

```typescript
// In @cms/astro runtime — runs on every page request
const previewToken = Astro.url.searchParams.get('cms_preview')
if (previewToken) {
  // Validate token with CMS API
  // If valid: fetch draft document instead of published
  // Add preview banner to page: "Preview mode — viewing unpublished content"
}
```

**`@cms/sdk` — preview mode:**

```typescript
const cms = new CMSClient({
  url: import.meta.env.CMS_URL,
  previewToken: Astro.url.searchParams.get('cms_preview') ?? undefined,
})
// All queries now return draft content if a valid preview token is provided
```

**Non-Astro frameworks:**

The preview protocol is framework-agnostic. Any frontend that can:

1. Read a `cms_preview` query param
1. Call `GET /api/preview/validate?token=<token>` to validate it
1. Pass the token in SDK requests

…supports live preview. Documented in `docs/preview.md` with examples for Next.js, Nuxt, and SvelteKit.

**Done when:** Preview token generates correctly. Preview URL opens the page in preview mode showing draft content. Preview banner appears on the page. Token expiry works — expired tokens return 401. Non-Astro integration documented with working code examples.

## Task 09 — CMS Update Notifications

**What it is:** A simple notification system that tells site owners when a new version of the CMS is available. Nothing more. No server-side updates, no lockfile management, no rollback system. Just an informational banner that something new is ready.

-----

### Why this is the right scope

Applying CMS updates involves package management, lockfile commits, migrations, and deployment — things that should happen from the developer’s local machine and go through version control. Automating this server-side creates lockfile drift and deployment conflicts that are confusing even for developers. For non-technical users it would be incomprehensible.

The right pattern is the same as any package manager or app store: **notify that something is available, let the developer decide when and how to apply it.**

-----

### New API routes

```
GET  /api/admin/updates/check     Check if a newer version is available
```

That’s it. One endpoint.

-----

### `GET /api/admin/updates/check`

**Development mode** (tracking `main` branch of `github.com/Kritano/Kritano-cms`):

Calls the GitHub API at `https://api.github.com/repos/Kritano/Kritano-cms/commits/main`, compares the latest commit SHA against the locally running version.

```typescript
{
  mode: 'development',
  updateAvailable: true,
  current: {
    sha: 'abc123',
    shortSha: 'abc123',
    committedAt: '2025-06-01T12:00:00Z',
  },
  latest: {
    sha: 'def456',
    shortSha: 'def456',
    committedAt: '2025-06-03T09:00:00Z',
    commitsAhead: 7,
  },
  recentCommits: [
    { sha: 'def456', message: 'Add plugin sandbox graceful fallback', date: '...' },
    { sha: 'cde345', message: 'Fix media folder deletion', date: '...' },
  ]
}
```

**Release mode** (tracking npm, once stable versions are published):

```typescript
{
  mode: 'release',
  updateAvailable: true,
  current: { version: '0.2.0' },
  latest: { version: '0.3.0' },
  updateType: 'minor',    // 'patch' | 'minor' | 'major'
  changelogUrl: 'https://github.com/Kritano/Kritano-cms/blob/main/CHANGELOG.md'
}
```

Mode is determined by `CMS_UPDATE_CHANNEL` in `.env`. Defaults to `development`.

The check runs automatically once per day as a BullMQ scheduled job. Result is cached in the database — the admin UI reads the cache, not the live API, so there’s no latency on page load.

-----

### Admin UI — update notification

A small, unobtrusive notification in the admin. Not a full page, not a modal. A banner at the top of the Dashboard and a badge on the Deployment sidebar item.

**No update available — nothing shown.** No “you’re up to date” message either. Absence of notification = everything is fine.

**Update available — subtle banner on dashboard:**

```
↑ CMS update available — 7 new commits since your last update.
  [View changes ↗]   [How to update ↗]
```

Clicking **View changes** opens the GitHub commits page for `Kritano/Kritano-cms` in a new tab.

Clicking **How to update** opens the docs page explaining the local update process.

**Deployment sidebar badge:** A small numbered badge showing how many commits are available. Disappears once the running version matches latest.

**Full detail in Deployment → Updates tab:**

```
Updates

Current version
  Commit abc123 — deployed 3 Jun 2025

Latest available
  Commit def456 — 5 Jun 2025 — 7 commits ahead

Recent changes:
  • Add plugin sandbox graceful fallback
  • Fix media folder deletion with nested items
  • Improve search indexing performance
  • ... 4 more

How to update:
  Run these commands in your portfolio project locally:

  bun update @cms/core @cms/admin @cms/astro @cms/sdk @cms/cli
  bun run dev     ← test locally first
  git add bun.lock && git commit -m "chore: update CMS"
  git push        ← your GitHub Action handles the server deploy

  [Copy commands]   [View full changelog ↗]
```

A **Copy commands** button copies the four-line update sequence to clipboard. That’s the most helpful thing the UI can do.

**For release mode** the message adapts:


For major version updates, add a single line of context:

```
⚠ Major update — read the migration guide before updating.
[Migration guide ↗]
```

### Dismiss

A small **Dismiss** link on the banner. Snoozes the notification for 7 days. Does not affect the badge on Deployment. Stored in the admin user’s preferences, not a global setting — each admin user controls their own notification state.

-----

### Database addition

