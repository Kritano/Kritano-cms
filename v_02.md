## Task 02 — API — Users & Roles

**What it is:** Role management, per-collection permissions, user invitation flow, two-factor authentication, and activity logging.

**New API routes:**

```
-- Roles
GET    /api/admin/roles              List all roles
POST   /api/admin/roles              Create custom role
GET    /api/admin/roles/:id          Get role + permissions
PUT    /api/admin/roles/:id          Update role permissions
DELETE /api/admin/roles/:id          Delete (system roles cannot be deleted)

-- Users
GET    /api/admin/users              List users with their roles
POST   /api/admin/users/:id/roles    Assign role to user
DELETE /api/admin/users/:id/roles/:roleId  Remove role from user
DELETE /api/admin/users/:id          Deactivate user (soft delete)

-- Invitations
POST   /api/admin/invitations        Send invitation email
GET    /api/admin/invitations        List pending invitations
DELETE /api/admin/invitations/:id    Revoke invitation
POST   /api/auth/accept-invitation   Accept invitation (creates account)

-- Two-factor auth
POST   /api/auth/2fa/setup           Generate TOTP secret + QR code
POST   /api/auth/2fa/verify          Verify TOTP code and enable 2FA
POST   /api/auth/2fa/disable         Disable 2FA (requires password)

-- Activity log
GET    /api/admin/activity           List activity (paginated, filterable)
```

**Permission system:**

The permissions object on each role is a flexible JSON structure:

```typescript
interface Permissions {
  '*'?: boolean                          // Super admin — all access
  content?: boolean | {
    read?: boolean
    create?: boolean
    update?: boolean
    update_own?: boolean                 // Can only update own documents
    delete?: boolean
    publish?: boolean
  }
  media?: boolean | {
    read?: boolean
    upload?: boolean
    delete?: boolean
  }
  users?: boolean
  settings?: boolean
  forms?: boolean
  redirects?: boolean
  webhooks?: boolean
  deployment?: boolean
}
```

**Per-collection permission override:**

Roles can have collection-specific overrides:

```typescript
{
  content: { read: true, create: true },
  collections: {
    'article': { publish: true },       // Can publish articles but not other content types
    'page': { update: false }           // Cannot edit pages
  }
}
```

**Auth middleware update:**

The existing JWT middleware needs extending to check permissions on every admin route. Create a `requirePermission(permission: string)` middleware:

```typescript
// Usage on routes
app.get('/api/admin/users', requireAuth, requirePermission('users'), handler)
app.post('/api/:collection', requireAuth, requirePermission('content.create'), handler)
```

**Invitation flow:**

1. Admin POSTs to `/api/admin/invitations` with email and role_id
1. Server generates a secure token, stores in invitations table with 7-day expiry
1. Sends invitation email via configured SMTP: “You’ve been invited to [site name]. Click to create your account.”
1. Recipient clicks link → frontend route `/admin/accept-invitation?token=xxx`
1. Frontend POSTs token + name + password to `/api/auth/accept-invitation`
1. Server validates token, creates user, assigns role, marks invitation accepted
1. User is logged in and redirected to admin dashboard

**Two-factor auth (TOTP):**

- Use `otplib` for TOTP generation and verification
- Setup: generate secret → return base32 secret + otpauth URL for QR code
- Verify: user submits 6-digit code → validate against secret → if valid, store encrypted secret on user record, set `two_factor_enabled: true`
- Login flow: if user has 2FA enabled, after password verification return a `requires_2fa` flag with a temporary token → frontend shows TOTP input → POST token + code to `/api/auth/2fa/challenge` → if valid, return full JWT

**Activity logging:**

Every significant action should log to the activity_log table. Create an `activityLogger` helper:

```typescript
await activityLogger.log({
  userId: req.user.id,
  action: 'document.published',
  resource: 'article',
  resourceId: doc.id,
  metadata: { title: doc.title }
})
```

Log these events: `document.created`, `document.updated`, `document.published`, `document.unpublished`, `document.deleted`, `media.uploaded`, `media.deleted`, `user.invited`, `user.created`, `user.role_changed`, `settings.updated`

**Done when:** All role routes work. Permission middleware blocks unauthorised access correctly. Invitation email sends and acceptance flow creates user with correct role. 2FA setup and verification work. Activity log records events correctly.

## Task 03 — API — Revision History

**What it is:** Automatic document revision snapshots and restore functionality.

**New API routes:**

```
GET    /api/:collection/:id/revisions          List revisions (newest first, max 50)
GET    /api/:collection/:id/revisions/:revId   Get a specific revision's data
POST   /api/:collection/:id/revisions/:revId/restore  Restore document to this revision
```

**Revision creation:**

A revision is created automatically on every document save. Hook into the existing PATCH/PUT handlers:

```typescript
// Before saving the update, snapshot the current state
await db.insert(revisions).values({
  documentId: doc.id,
  collection: collectionName,
  data: currentDocumentData,   // full document snapshot as JSONB
  createdBy: req.user.id,
})

// Then apply the update
await db.update(collection).set(updateData).where(eq(id, doc.id))
```

**Revision limit:**

After inserting a new revision, delete oldest revisions beyond the limit of 50:

```sql
DELETE FROM revisions
WHERE document_id = $1
  AND id NOT IN (
    SELECT id FROM revisions
    WHERE document_id = $1
    ORDER BY created_at DESC
    LIMIT 50
  )
```

**Restore:**

Restoring a revision creates a new revision (of the current state, before restore) then applies the revision data as an update. Never destructive — the current state is always preserved as a revision before overwriting.

**Revision list response shape:**

```typescript
interface RevisionSummary {
  id: string
  createdAt: string
  createdBy: {
    id: string
    name: string
  } | null
  // A brief label — 'Published', 'Saved', 'Restored from [date]'
  label: string
}
```

**Done when:** Every document save creates a revision. Revisions list returns correctly sorted, max 50. Restore applies the revision data correctly and creates a new revision of the pre-restore state.

## Task 04 — API — Scheduled Publishing

**What it is:** Schedule a document to publish at a future date and time. A background job checks for due items and publishes them.

**New API routes:**

```
POST   /api/:collection/:id/schedule    Schedule a publish
DELETE /api/:collection/:id/schedule    Cancel a scheduled publish
GET    /api/:collection/:id/schedule    Get current schedule for a document
```

**Schedule request body:**

```typescript
{
  scheduledFor: '2025-06-01T09:00:00',   // ISO datetime
  timezone: 'Europe/London'              // IANA timezone string
}
```

**BullMQ scheduler:**

On receiving a schedule request:

1. Store in `scheduled_publishes` table
1. Calculate the UTC timestamp from the provided datetime + timezone
1. Add a delayed BullMQ job: `scheduledPublishQueue.add('publish', { documentId, collection }, { delay: msUntilPublish })`
1. The job processor calls the existing publish logic when it fires

**On cancel:**

1. Update `scheduled_publishes` status to `cancelled`
1. Remove the BullMQ job by job ID (store job ID on the scheduled_publishes record)

**Document status for scheduled items:**

Add a `scheduled` status alongside `draft` and `published`. A document that is scheduled shows as scheduled in the admin — not draft, not published. On the scheduled time it becomes published.

**Timezone handling:**

Use the `date-fns-tz` library for timezone-aware datetime operations. Never store local times — always convert to UTC for storage and job scheduling.

**Done when:** Can schedule a document, confirm it appears as scheduled in the list view, cancel the schedule. In a test environment, set a schedule 10 seconds in the future and verify the document publishes automatically.

## Task 05 — API — Webhooks

**What it is:** Outbound webhook delivery system. When content events occur, notify configured external endpoints.

**New API routes:**

```
GET    /api/admin/webhooks              List webhooks
POST   /api/admin/webhooks              Create webhook
GET    /api/admin/webhooks/:id          Get webhook
PUT    /api/admin/webhooks/:id          Update webhook
DELETE /api/admin/webhooks/:id          Delete webhook
GET    /api/admin/webhooks/:id/deliveries  Delivery log (paginated)
POST   /api/admin/webhooks/:id/test     Send a test delivery
```

**Available events:**

```typescript
type WebhookEvent =
  | 'content.created'
  | 'content.updated'
  | 'content.published'
  | 'content.unpublished'
  | 'content.deleted'
  | 'media.uploaded'
  | 'media.deleted'
  | 'form.submitted'
  | 'user.created'
```

**Delivery:**

Webhook delivery runs as a BullMQ job — never in the request handler. When an event occurs:

1. Find all active webhooks subscribed to that event
1. For each webhook, enqueue a delivery job
1. Job processor sends POST to the webhook URL:

```typescript
// Payload shape
{
  event: 'content.published',
  timestamp: '2025-01-01T12:00:00Z',
  site: 'https://mysite.com',
  data: {
    id: 'xxx',
    collection: 'article',
    document: { /* full document */ }
  }
}
```

**HMAC signing:**

If the webhook has a secret configured, add an `X-CMS-Signature` header:

```typescript
const signature = crypto
  .createHmac('sha256', webhook.secret)
  .update(JSON.stringify(payload))
  .digest('hex')
// Header: X-CMS-Signature: sha256=<signature>
```

**Retry logic:**

- On delivery failure (non-2xx response or network error): retry with exponential backoff
- Retry schedule: 1 min, 5 min, 30 min, 2 hours, 8 hours (5 attempts total)
- After 5 failures: mark delivery as permanently failed, do not retry
- Auto-disable webhook after 10 consecutive permanent failures

**Delivery log:**

Every delivery attempt logged to `webhook_deliveries` — success or failure, response code, response body (truncated to 1000 chars), duration in ms.

**Test delivery:**

`POST /api/admin/webhooks/:id/test` sends a test payload immediately, bypassing the queue. Returns the delivery result synchronously.

**Done when:** Webhooks receive events. HMAC signature is correct. Retry logic fires on failure. Delivery log records all attempts. Test delivery works.

## Task 06 — API — Redirects

**What it is:** Redirect storage and nginx-level redirect middleware.

**New API routes:**

```
GET    /api/admin/redirects            List redirects (paginated)
POST   /api/admin/redirects            Create redirect
PUT    /api/admin/redirects/:id        Update redirect
DELETE /api/admin/redirects/:id        Delete redirect
POST   /api/admin/redirects/import     Bulk import from CSV
GET    /api/admin/redirects/export     Export as CSV
POST   /api/admin/redirects/check-chains  Detect chains in current redirects
```

**Redirect middleware:**

Add middleware to the Hono server that checks incoming requests against the redirects table:

```typescript
app.use('*', async (c, next) => {
  const path = new URL(c.req.url).pathname
  const redirect = await db.query.redirects.findFirst({
    where: eq(redirects.fromPath, path)
  })
  if (redirect) {
    // Increment hit counter
    await db.update(redirects)
      .set({ hits: sql`hits + 1` })
      .where(eq(redirects.id, redirect.id))
    return c.redirect(redirect.toPath, redirect.type)
  }
  await next()
})
```

**Slug change detection:**

When a document’s slug is updated via the API, automatically suggest a redirect. Hook into the PATCH handler:

```typescript
// If slug field is changing
if (update.slug && update.slug !== currentDoc.slug) {
  // Return a suggestion in the response
  responseExtras.redirectSuggestion = {
    from: `/${collection}/${currentDoc.slug}`,
    to: `/${collection}/${update.slug}`,
    type: 301
  }
}
```

The admin UI picks this up and prompts: “Slug changed — create a 301 redirect from the old URL? [Yes] [No]”

**Chain detection:**

`POST /api/admin/redirects/check-chains` scans all redirects and returns any chains (A → B where B is also a `from_path`). Returns an array of chain objects so the admin UI can display them clearly.

**CSV import format:**

```
from_path,to_path,type
/old-page,/new-page,301
/another-old,https://external.com,302
```

**Done when:** Redirects fire correctly at the server level. 301 and 302 both work. Slug change suggestion appears in the API response. Chain detection returns correct results. CSV import and export work.

## Task 07 — API — API Keys

**What it is:** API key generation for headless frontend access and the MCP server.

**New API routes:**

```
GET    /api/admin/api-keys             List API keys (never show full key)
POST   /api/admin/api-keys             Create new key
DELETE /api/admin/api-keys/:id         Revoke key
```

**Key generation:**

```typescript
// Generate a secure random key
const rawKey = `cms_live_${crypto.randomBytes(32).toString('hex')}`
const keyPrefix = rawKey.substring(0, 16)  // 'cms_live_xxxxxxxx'
const keyHash = await bcrypt.hash(rawKey, 10)

// Store only the hash and prefix
await db.insert(apiKeys).values({
  name: body.name,
  keyHash,
  keyPrefix,
  permissions: body.permissions,
  expiresAt: body.expiresAt ?? null,
  createdBy: req.user.id,
})

// Return the full key ONCE — never stored, never retrievable again
return { key: rawKey, prefix: keyPrefix }
```

**Auth middleware update:**

Extend the auth middleware to accept API keys alongside JWT tokens:

```typescript
// Check Authorization header
const auth = c.req.header('Authorization')
if (auth?.startsWith('Bearer cms_live_')) {
  // API key auth
  const key = auth.replace('Bearer ', '')
  const prefix = key.substring(0, 16)
  const keyRecord = await db.query.apiKeys.findFirst({
    where: eq(apiKeys.keyPrefix, prefix)
  })
  if (keyRecord && await bcrypt.compare(key, keyRecord.keyHash)) {
    // Update last_used
    await db.update(apiKeys).set({ lastUsed: new Date() })
    c.set('user', { id: 'api_key', permissions: keyRecord.permissions })
    return next()
  }
  return c.json({ error: 'Invalid API key' }, 401)
}
// Fall through to JWT auth
```

**Scopes:**

```typescript
type ApiKeyScope =
  | 'content:read'       // Read published content
  | 'content:write'      // Create and update content
  | 'content:publish'    // Publish and unpublish
  | 'media:read'         // List and read media
  | 'media:write'        // Upload media
  | 'schema:read'        // Read collection schemas (needed for MCP)
```

**Done when:** API key creation returns the full key exactly once. Subsequent requests with the key authenticate correctly. Revoked keys are immediately rejected. Scope enforcement works — a `content:read` key cannot create documents.

## Task 10 — Admin UI — Forms Builder

**What it is:** Visual form builder, form management, submissions viewer, and CSV export.

-----

### Performance contract

**Forms on CMS-built sites must ship zero JavaScript by default.** The CMS promises Lighthouse 100 structurally — forms cannot compromise that. Every rendering and submission decision below follows from this constraint.

There are three rendering contexts for a form. Each has a different approach:

|Context                    |Rendering                                           |JS required               |
|---------------------------|----------------------------------------------------|--------------------------|
|Astro (default frontend)   |Server-side rendered HTML at build time             |None                      |
|Non-Astro headless frontend|Developer uses `@cms/sdk` to fetch schema and render|Developer’s choice        |
|Third-party site (not CMS) |Embed script as progressive enhancement             |Async, non-blocking, < 5kb|

-----

### Rendering — Astro (default, zero JS)

Forms on Astro-based sites render as plain HTML `<form>` elements at build time. No JavaScript, no external script, no network request on page load.

```astro
---
// components/Form.astro — part of @cms/astro
import { CMSClient } from '@cms/sdk'

const { formSlug } = Astro.props
const cms = new CMSClient({ url: import.meta.env.CMS_URL })
const form = await cms.forms.get(formSlug)
---

<form
  method="POST"
  action={`/api/forms/${form.slug}/submit`}
  class="cms-form"
>
  {form.fields.map(field => (
    // Renders correct semantic HTML input per field type
    // text → <input type="text">
    // email → <input type="email">
    // textarea → <textarea>
    // select → <select><option>...</select>
    // checkbox → <input type="checkbox">
    // file → <input type="file">
    // date → <input type="date">
    // honeypot → <input type="text" name="_hp" tabindex="-1" aria-hidden="true" style="display:none">
  ))}
  <button type="submit">{form.settings.submitLabel || 'Submit'}</button>
</form>
```

Lighthouse sees a plain HTML form. Zero performance impact.

**Submission handling — standard POST, no JS:**

The form POSTs to `/api/forms/:slug/submit`. The API handler:

1. Validates all fields server-side
1. Checks honeypot — if filled, silently discard and redirect to success
1. On success: `302` redirect to `?submitted=true`
1. On validation error: `302` redirect back with `?error=field_name&message=...`

The Astro page reads the query params and renders the success message or error inline. No JavaScript involved at any point.

```astro
---
// pages/contact.astro
const submitted = Astro.url.searchParams.get('submitted')
const error = Astro.url.searchParams.get('error')
---

{submitted && <p class="success">Thanks! We'll be in touch.</p>}
{error && <p class="error">{Astro.url.searchParams.get('message')}</p>}

<Form formSlug="contact" />
```

**Progressive enhancement — inline validation (optional, < 5kb):**

For sites that want inline field validation without a full page reload, `@cms/astro` provides an optional enhancement script. It is:

- Loaded with `defer` — never blocks rendering or parsing
- Under 5kb gzipped
- Intercepts the form submit, validates fields client-side, shows errors inline
- Falls back to the standard POST if JS fails or is unavailable
- Opt-in only — not included by default

```astro
---
// Opt in to inline validation
---
<Form formSlug="contact" enhance={true} />
<!-- Adds: <script defer src="/api/forms/enhance.js"></script> -->
```

**File upload fields:**

File fields use the standard HTML `<input type="file">` and submit via `multipart/form-data` POST. No JS required. For sites that opt into the `enhance` script, a progress indicator is shown during upload — but the upload works without it.

-----

### Rendering — non-Astro headless frontends

Developers using Next.js, Nuxt, SvelteKit etc. fetch the form schema via `@cms/sdk` and render it themselves using their framework’s components. They own the rendering and JS budget entirely. The SDK provides the schema, the API receives the submission.

```typescript
// Next.js example
const form = await cms.forms.get('contact')
// Developer renders form.fields using their own components
// Submits to POST /api/forms/contact/submit
```

-----

### Rendering — third-party embed (non-CMS sites only)

For users who want to embed a CMS form on a site they don’t control — a static HTML page, a Webflow site, a WordPress site — a JavaScript embed is available. This is explicitly a third-party use case. The Lighthouse impact is on the host site’s score, not on any CMS-built site.

The embed script is:

- Loaded `async` — never blocks the host page’s rendering
- Under 5kb gzipped
- No framework dependencies — vanilla JS only
- Renders after the page’s `load` event — LCP and FCP are never affected
- Accessible — renders the same semantic HTML as the Astro component

```html
<!-- Third-party embed — not for use on CMS-built sites -->
<div data-cms-form="contact"></div>
<script src="https://mysite.com/api/forms/embed.js" async></script>
```

The embed snippet is shown on the form settings page under a clearly labelled section: **“Embed on a non-CMS site”** — with a note explaining that for CMS-built Astro sites, the `<Form>` component should be used instead.

**`POST /api/forms/:slug/submit` response behaviour:**

This endpoint always responds with a redirect, not JSON. This is intentional — it supports the standard HTML form POST pattern without requiring JavaScript.

```
Success  → 302 redirect to Referer?submitted=true
           or 302 redirect to settings.redirectUrl if configured
Error    → 302 redirect to Referer?error=field_name&message=Field+is+required
Honeypot → 302 redirect to Referer?submitted=true (silent discard)
```

For JS-based submissions (embed script, SDK), the same endpoint is used but the response is followed and the redirect destination’s query params are read to determine outcome.
